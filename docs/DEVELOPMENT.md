# Local Development

## Project Layout

```
vestia/
├── backend/    FastAPI app, SQLAlchemy models, rules engine, tests
├── frontend/   Next.js app (App Router), Zustand stores, components
├── data/       (gitignored) shared volume mount-point for Docker
└── docs/       this documentation
```

See [ARCHITECTURE.md](./ARCHITECTURE.md) for how the pieces fit together.

## Running Both Services

Two terminals:

```bash
# Terminal 1
cd backend && source .venv/bin/activate
uvicorn app.main:app --reload --port 8000

# Terminal 2
cd frontend
npm run dev
```

Frontend hot-reloads on save. Backend `--reload` restarts on Python file
changes. `next.config.mjs` rewrites `/api/*` and `/uploads/*` to
`localhost:8000`, so no `.env.local` changes are needed for default ports.

## Database Migrations

Schema changes go through Alembic. After editing
`backend/app/database/models.py`:

```bash
cd backend
alembic revision --autogenerate -m "describe your change"
alembic upgrade head
```

`alembic/env.py` reads `DATABASE_URL` from `app.config.settings` and uses
`render_as_batch=True`, so autogenerated migrations work correctly against
SQLite's `ALTER TABLE` limitations and against PostgreSQL unchanged.

To reset the dev database entirely:

```bash
rm -f data/db/vestia.db
alembic upgrade head
python -m app.database.seed --clear
```

## Testing

```bash
cd backend
python -m pytest tests/ -v                    # all 174 tests
python -m pytest tests/unit/ -v                # rules engine + repositories (138)
python -m pytest tests/api/ -v                 # endpoint contract tests (36)
python -m pytest tests/unit/test_color_rules.py -v   # single module
```

`tests/api/conftest.py` spins up a `TestClient` with an in-memory SQLite DB
and temp upload/FAISS directories per test — no shared state, safe to run
in parallel with `pytest-xdist` if desired.

Frontend:

```bash
cd frontend
npm run lint        # ESLint
npm run build       # type-check + production build
```

## Adding a New Occasion or Rule

Occasion definitions live in
`backend/app/rules/occasion_rules.OCCASION_RULES` — add an entry with
`required_categories`, `optional_categories`, and `preferred_styles`, then
add the same name to `OCCASION_LABELS` in
`frontend/src/types/outfit.ts` for UI display. Add a corresponding row to
the `occasion_types` table via a migration if you want it queryable from
SQL (the rules engine itself reads the Python constant for performance).

Color/style/season compatibility tables are similarly plain Python dicts in
`backend/app/rules/*.py` — each has a dedicated test file in
`backend/tests/unit/` to extend alongside any changes.

## Code Style

- Backend: type-hinted Python, `from __future__ import annotations`
  throughout, Pydantic v2 schemas separate from SQLAlchemy models.
- Frontend: strict TypeScript, Zustand for state (no Redux), Tailwind
  utility classes only — design tokens in `tailwind.config.ts`
  (`canvas`/`surface`/`ink`/`gold`/`sage`/`clay`).
- No AI/LLM calls anywhere in the recommendation path — `rules/` must
  remain pure functions of item metadata for testability and determinism.
